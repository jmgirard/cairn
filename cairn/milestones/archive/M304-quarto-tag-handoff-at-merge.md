# M304: Hand over the tag commands when a merge raises the version

**Status:** done (2026-10-20, PR #318 https://github.com/jmgirard/cairn/pull/318)

**Goal:** In a quarto-extension repo, the close after a merge that raised the version hands the user the commands that tag and release it.

**Outcome:** `/milestone-review` step 10 gains a "Tag handoff" paragraph (owner mode, quarto-extension profile, a merge this run made), and `/hotfix` step 7 runs it on the merge commit of the PR it merged, after its own fetch and fast-forward; a dirty tree or failed pull is named and the arm still runs. The arm reads `<merge sha>` with `gh pr view --repo <base-repo> --json mergeCommit`, finds the one `_extensions/<name>/_extension.y*ml` with `git ls-tree` at that commit, and runs `cairn_versions.py --changed-by <merge sha>`. When a version prints and `git ls-remote --tags origin` has no `v<version>`, it writes the notes (the changelog section for the version, else the first-parent commit subjects since the previous `v*` tag) to `cairn-notes-<owner>-<repo>-v<version>.md` in the system temp directory, shows them, and fences `git tag -a` (left out for an unpushed local tag), `git push origin v<version>`, and, for a GitHub origin with `gh`, `gh release create --notes-file "<file>" --verify-tag`, each labeled, before the next-action commands; cairn never runs them. Guest mode, other profiles, resume route (a), the guest hygiene run, the hotfix merged-PR re-entry, companion merges, an empty merge commit, and a script error fence none. The rulebook's D-050 rule, README (release row and "does NOT do"), CHANGELOG, the profile's version-rise consequence, DESIGN, and the `cairn_versions.py` docstring name the handoff. embedpdf: `--changed-by a68951d` printed `1.2.9`, `cf71a53` printed nothing.

**Decisions:** D-202 (annotates D-050: a merge that raised the version is the release the user approved; supersedes D-048's wiring clause to add the `/hotfix` close).
