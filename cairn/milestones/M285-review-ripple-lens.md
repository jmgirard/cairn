## Goal

Copilot reviews a head whose header names the PR, and cairn's own review reads the rest of the repo for text that the diff made stale.

## Scope

**In:** the order of `/milestone-review` step 2's Copilot arm and step 8's sentence about the header record. A ripple reviewer on Haiku in both review modes of step 5. Two questions in the diff-bug lens's instruction, one on await races and one on untried procedure paths. tracking-rules "Model and agent strategy", README, CHANGELOG, a D-entry, and the hand-run guard `skills/tests/test_review_fanout.py`.

**Out:** `/hotfix`, which has no review fan-out and no milestone header. A repo whose GitHub settings start a Copilot review when a PR opens: Copilot then reviews before the header commit, and the arm cannot change that. The five-review check of the ripple lens's yield, which the falsifier names: it lives in the candidate row "Ripple lens yield check". The Copilot threads that asked for mutation entries for hand-run guards (4 threads), because this repo's test doctrine owes none.

## Acceptance criteria

- [x] AC1: `/milestone-review` step 2's Copilot arm runs in this order. It pushes the branch. It opens the PR, unless the header already names an open PR. For a new PR, it adds the PR's URL to the `Branch/PR` header in a commit and pushes that commit. Then it runs the state query and requests Copilot on `none`. If the branch push or the create fails, the arm reports the failure in one line and requests nothing. If the header already names a closed PR, the create runs and the arm adds the new URL beside the old one. If the header push fails, the arm reports the failure in one line and still runs the state query and the request. That commit then stays local until step 6's checkpoint push carries it. Neither the arm nor step 8 says that step 6's push carries the header record on the normal path, and step 8 cites the new D-entry.
- [x] AC2: Step 5 spawns a ripple reviewer on Haiku, with the slug `ripple`, in both review modes. The routing bullets say so: an internal-tier docs-only diff gets the Opus diff-bug lens and the ripple lens, and any other diff gets four lenses. The ripple reviewer's instruction tells it to list each rule statement, term, number, identifier, command, flag, and path that the diff removes or changes. For each item, it runs `git grep` on the tracked files at the branch head. It searches for the old form and for other statements of the same fact. It reports each line outside the diff's added lines that now disagrees with the diff, with its file and line. It leaves out history records: `cairn/milestones/`, `cairn/DECISIONS.md`, `cairn/legacy/`, `cairn/reviews/`, and the CHANGELOG sections of released versions. It does not report a line that states a dated measurement or record of an earlier setup. A diff that removes or changes nothing gives the report "no ripple evidence" and zero findings. The lens ranks its own findings, and the agent settles them like the findings of every lens.
- [x] AC3: The diff-bug lens's instruction in step 5 gains two questions, and the lens reports what they find as ranked findings. (a) The diff adds or changes code that awaits: an `await`, a promise callback, or a timer. For each value that the code reads or sets before an await and relies on after it, can another handler change the value in between? Examples are a second press, a session end, and a later read. (b) The diff adds or changes a skill procedure step. Does the step hold on at least these five paths? The first is a first run with no remote branch, PR, or file yet. The second is guest mode, with `--repo <base-repo>` and a fork or base remote. The others are a PR whose head is on a fork, a dirty working tree, and a remote that moved ahead.
- [x] AC4: tracking-rules "Model and agent strategy" lists the ripple lens under Haiku subagents. Its review bullet names the ripple lens in both modes and counts four distinct-evidence reviewers in the fan-out. README's review paragraph names the four-lens fan-out and the two-reviewer mode for an internal docs-only diff. The step-5 slug sentence names `ripple`. Run this command: `git grep -n -i -E "three-lens|three lenses|three distinct|three reviewers|three-reviewer|two lenses|other two|single reviewer|single-reviewer|one reviewer|one Opus" -- README.md CLAUDE.md cairn/DESIGN.md cairn/LESSONS.md skills hooks scripts`. - [x] AC5: An unreleased CHANGELOG entry states three changes: the header push before the Copilot request, the ripple lens in both review modes, and the two diff-bug questions. A D-entry records the decision. It supersedes D-153's clause that the step-6 checkpoint push carries the header record. It supersedes D-112's lens count and its one-reviewer docs-only mode. It annotates D-174, because Haiku gains a third review role. It passes D-108's door on its retained trigger, with a shipped defect for each new rule. For the ripple lens, this is README's `/hotfix` row, which M73 shipped still describing the old trigger and M74 fixed. For question (a), these are the pane races fixed after they shipped (M243, M255, M256, M260, M278). For question (b), this is the guest push that did not find the fork, which M234 fixed. Its falsifier reads one window: the first five reviews that run the ripple lens. If the lens gives no fixed finding in that window, the lens is removed. Otherwise, if Copilot finds stale text in the lens's domain that the lens missed on two or more of those PRs, the lens moves to Opus.
