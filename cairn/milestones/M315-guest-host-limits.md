# M315: Keep guest sessions within the host's limits

- **Status:** review

## Goal

`/milestone-review` and `/hotfix` check two caps on the operator's open PRs on a repo, one for bug fixes and one for features, before they open a new PR, in owner and guest mode. In a repo the operator does not own, sessions also follow set rules for review threads, bot comments, other people's issues, and agreeing on a feature's design with a maintainer first.

## Scope

**In:** two open-PR caps, read from the `# Bug-fix PR cap: N` (default 3) and `# Feature PR cap: N` (default 1) header lines of `cairn/PROFILE.md`, checked in owner and guest mode by `/milestone-review` and `/hotfix` before a new PR opens; a PR counts by its head branch. The caps in the session-start text in both modes, and four guest rules in the guest session-start text (`hooks/session_context.py`, with a cap reader in `hooks/cairn_common.py`) and in tracking-rules "Collaboration mode": no resolve of a thread a person started, no reply to a bot, limits on closing another person's issue, and a feature or a change of behavior planned only after a maintainer agrees with its design. README, CHANGELOG, DESIGN's header-line list, and a D-entry.

**Out:** the one-comment Copilot reply → M314. When the Copilot round runs: guest repos keep the opt-in line (the user's answer). A hook that blocks `gh pr create` or `gh issue close` by count: the rules are instructions to the session, and only the two skills check the caps. The caps at `/milestone-implement`'s branch cut: the handoff is where a PR opens. `/hotfix`'s follow-up PR after its merged-PR re-entry, its re-land of a contributor's work, and companion PRs read no cap: each carries work from a PR that already exists. A check in `/milestone-plan` that an issue shows a maintainer's agreement: the issue-first rule is an instruction that applies before a plan starts (the user's answer). A guest repo where the operator merges their own PRs (easystats/datawizard) → candidate row.

## Acceptance criteria

- [x] AC1: In owner and guest mode, `/milestone-review` and `/hotfix` read the operator's open PRs on `<base-repo>` with `gh pr list --repo <base-repo> --author @me --state open --limit 100 --json number,url,headRefName` at these sites: in `/milestone-review`, step 2's Copilot arm, before step 7's merge chip is posed in owner mode (step 8 opens the PR on approval), and before step 8's push in guest mode after its push-access and stack-base reads, each only when that step will open a PR: the header names no open PR and the review is not on resume route (b); in `/hotfix`, step 1 for an authored fix from a bug report, before step 2 cuts its branch (not the merged-PR re-entry's follow-up). A listed PR counts by its head branch, not its content: a `headRefName` that starts with `hotfix-` is a bug fix and any other a feature, and a stacked milestone's `<base-pr>` is not counted. `/hotfix` compares the bug-fix count with the bug-fix cap, and `/milestone-review` the feature count with the feature cap. A count at its cap or over it makes the skill push nothing, open no PR, leave any milestone status as it is, and stop with a close block that names the cap and each open PR of that kind; a list of 100 PRs counts as reaching both caps, and its close block says the list reached 100 in place of the PRs. A failed read stops the same way, naming the read and its error in place of the open PRs. `/milestone-review`'s close block fences `/milestone-review M<NNN>`, labeled as rerunning the review. A push to an already-open PR reads no cap. The bug-fix cap is N from a `# Bug-fix PR cap: N` line, and the feature cap N from a `# Feature PR cap: N` line, in the header of `cairn/PROFILE.md`, each read as the `# Collaboration mode:` line is read, when N matches `[1-9][0-9]?`, and 3 and 1 otherwise; the close block names each cap line in the header whose value it did not take.
